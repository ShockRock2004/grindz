# How a new exercise reaches a phone without a new APK

`catalog.ts` and `exerciseMuscles.ts` compile straight into the JS bundle, same as any other
source file — so historically, adding an exercise only reached a device inside a new APK
build. That is fine for the web app, which redeploys on every push anyway, but it means the
Android app was always at least one release behind whatever was actually in the repo.

This is the pipeline that closes that gap, without turning the mobile app into something that
downloads and runs arbitrary code (see "Why not EAS Update" below for why that line matters).

```
 developer edits                 CI regenerates              CDN serves it            phone picks it up
 catalog.ts / exerciseMuscles.ts  →  cdn/public/catalog.json  →  cdn.grindz.dev  →  on next app open
     (typed, autocompleted)         (.github/workflows/            /catalog.json      (catalogSync.ts)
                                      sync-catalog.yml)
```

## The four pieces

| Piece | File | Job |
|---|---|---|
| Source of truth | `apps/web/src/data/catalog.ts`, `exerciseMuscles.ts` | What a developer actually edits — unchanged from before this existed |
| Generator | `apps/web/scripts/gen-catalog-json.mts` | Imports both files via `tsx` and writes their exports as JSON |
| Auto-publish | `.github/workflows/sync-catalog.yml` | Runs the generator on every push to `main` that touches either source file, commits the JSON if it changed |
| Client | `apps/mobile/src/data/catalogSync.ts` | Fetches the JSON, caches it, swaps it in — see below |

`cdn/public/catalog.json` is the one *generated* file in this repo that also gets **committed** — everything else generated (`bodyMuscles.ts`) is regenerated by hand and committed the
same way, so this isn't a new pattern, just the same one pointed at a new output. The
alternative — generating it at Cloudflare deploy time instead of committing it — was rejected
because the CDN Worker is deliberately a zero-build static-assets deploy (see `cdn/README.md`);
adding a build step there to save one manual `npm run gen:catalog` was not a good trade.

## What the mobile app actually does with it

Two calls, both from `apps/mobile/src/lib/app-context.tsx`, in order, on every app launch:

1. **`hydrateCatalogFromCache()`** — instant, from `AsyncStorage`. This is what makes a
   *previously synced* exercise available with no signal, not just the ones bundled in the APK.
2. **`syncCatalogFromNetwork()`** — fetches `cdn.grindz.dev/catalog.json`, and if it is newer
   than what's cached, persists it and swaps it in.

Both fail soft, the same contract as the image-upload pipeline in `docs/IMAGES.md`: a bad
response, a timeout, a malformed payload — all of them just mean "keep showing whatever the
app already had." A stale exercise list is a much smaller problem than a broken one, and a
gym is exactly the kind of place a request might not land.

`data/catalog.ts` exports `CATALOG`, `CATALOG_BY_KEY` and `EXERCISE_TIPS` as **mutable
bindings**, not functions — every screen already reads them as `CATALOG.find(...)` or
`CATALOG_BY_KEY[key]`, and ES module bindings are live references, so a reassignment inside
`applyLiveCatalog()` is visible to every importer the next time it reads them. That swap alone
does not make anything re-render, though — mutating a module variable is invisible to React.
`CatalogCtx` in `app-context.tsx` exists purely to fix that: it carries nothing but a version
counter, and `App.tsx`'s `Shell` subscribes to it with one `useCatalog()` call, which is
enough — Shell's re-render cascades to every screen beneath it, none of which are memoized.

## Cache policy — the opposite of the images

Every other file under `cdn/public/` is cached `immutable` for a year, because exercise
*photos* are content-addressed: a changed photo ships under a new filename, so the old URL
never needs to change what it serves (see `docs/IMAGES.md`). `catalog.json` is the opposite —
the same URL is expected to change, that's the entire point — so `cdn/public/_headers` gives
it `max-age=300` instead: a device re-checks at most every five minutes. `scripts/check-cdn.mjs`
enforces both directions — it fails if `catalog.json` ever gets cached immutably, and (like
every other file) if it's missing entirely.

## Why not EAS Update

Expo has a real over-the-air update mechanism (`expo-updates` + EAS) that republishes the
entire JS bundle, not just data. It was considered and set aside for this specific problem:

- The actual ask was "a new exercise shows up" — data, not code. Shipping a mechanism that can
  silently replace arbitrary app logic is a much bigger blast radius than the problem needs.
- It requires a new account, a `runtimeVersion` policy, an EAS token in CI, and — because it
  changes the JS runtime itself — one more manual APK build just to embed the updates client
  before any of it works.
- A bad OTA push is a sharper footgun than a bad `catalog.json`: this pipeline's worst failure
  mode is "the exercise list didn't update," entirely contained by the fail-soft fetch above.
  A bad `expo-updates` push can white-screen the app for everyone who already has it installed.

If a future need is genuinely "ship a bug fix without a store-style release" rather than "ship
new data," that is the point to revisit EAS Update — it solves a different, larger problem
than this one.

## Adding a new exercise, end to end

Nothing about this changed the authoring step:

1. Edit `apps/web/src/data/catalog.ts` (the exercise, its tips) and `exerciseMuscles.ts` (which
   muscles it trains) — see `docs/IMAGES.md` for the image half, if it has a photo.
2. Push to `main`.
3. `sync-catalog.yml` regenerates and commits `cdn/public/catalog.json`; Cloudflare republishes
   it the same way it republishes an image commit.
4. Every phone that opens the app picks it up within the next `max-age` window — no APK, no
   store review, no reinstall.

`apps/mobile/src/data/catalog.ts`'s `BUNDLED_CATALOG` / `BUNDLED_TIPS` — the offline
fallback baked into the APK — are **not** part of this loop and do not need updating for a
device to see a new exercise. They only matter for a brand-new install, or a device that has
never once been online since installing; keep them roughly current so that case doesn't look
badly out of date, but there is no correctness requirement to touch them for every exercise.
